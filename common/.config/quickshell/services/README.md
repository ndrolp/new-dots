# Services

Place shared system integrations here, such as audio, network, and battery services.

## Cava

`Cava.qml` is the one `cava` process the shell shares. Each Cava bar element
calls `setDrawing(element, drawing)` as it starts or stops being drawn; cava
runs while any is drawn and stops otherwise. It listens to the default audio
output and restarts when the default changes. It computes the most bars any
drawn element asks for (its `barCount`, a bar profile option), restarting when
that changes, and each element resamples the frame down to its own count. Its
config is generated by `CavaOutput.js` and given to cava on stdin.

`silent` turns true once cava has printed only flat frames for
`CavaOutput.silenceDelay` (or isn't running), and the Cava bar element hides
meanwhile. A hidden Cava still counts as drawn, so cava keeps listening for the
sound that shows it again.

When cava exits on its own while drawn, it is tried again a while later and
`failureHint` says why the bars stay flat (missing, failed to start, or
stopped unexpectedly after printing frames). When to start, stop, restart and
retry is decided by plain functions in `CavaOutput.js` (`drawnChanged`,
`restartAsked`, `framePrinted`, `exited`, `retryDue`); `Cava.qml` only
carries the decisions out, so they are tested without Quickshell.

## Workspaces

`WorkspaceService.qml` is what the shell knows of Hyprland's workspaces and
windows, and how it acts on them. Which workspaces are listed (1 to 21), which
windows a workspace shows and the `hyprctl` commands that focus, move and create
are plain functions in `WorkspaceState.js`, tested without Quickshell. A move or
a new workspace that doesn't exist yet takes a second step, sending the workspace
to the monitor it was meant for, because Hyprland makes it on the focused monitor
or the one a rule names.

## Monitor setups

`MonitorSetups.qml` is the shell's one way to change the monitors. Displays and
the quick switch work out the entries they want with the plain functions in
`MonitorSetup.js` (`moved`, `withResolution`, `turnedOff`…) and hand them to
`apply(entries)`, which starts the 15-second countdown; `keep()` and `revert()`
answer it, and an unanswered one reverts. `entries`, `modesOf(port)` and
`savedSetups` are what there is to show, and `modules/MonitorChange.qml` shows
the countdown card and *Identify* on the screens. Hyprland owns the setups
(`docs/adr/0002-hyprland-owns-monitor-setups.md`): the shell writes
`~/.config/hypr/monitor-setups.json` atomically, then runs `hyprctl eval` on
`apply_now` in `hypr/modules/monitors/apply.lua`, which reads it without the
full config reload `hyprctl reload` would do.

`forget(combination)` removes a saved setup from the file and doesn't ask
Hyprland, so the monitors stay as they are until the next time it detects them.
Hyprland doesn't watch that file: only the config and the modules it requires.
It's refused during a countdown, when Revert would put the file back, and
`savedSetups` leaves out a change being tried out, which isn't saved yet.

A change has to be in the file for Hyprland to apply it, so it's in there before
it's kept, with what to go back to under `unkept` in the same write. Revert
applies the previous arrangement through the file, then puts the file back
exactly as it was, or removes it if there was none; if the shell stops during a
countdown it finds `unkept` when it starts and reverts. `apply` refuses a setup
that leaves every screen dark. The steps are `MonitorChange.js`, snapping is
`MonitorArrangement.js` and mode and scale choices are `MonitorModes.js`, whose
`nearestScale` is the search Hyprland does, so a preset it won't take snaps
before it's written. All are tested without Quickshell. With a closed lid and an
external monitor the laptop screen is no part of a setup, by the same rule as
`split_by_lid` in `hypr/modules/monitors/setups.lua`: the two must stay in step.

`QuickSwitch.js` holds the quick switch's choices and the entries each one builds,
for the panel on SUPER+P and anything else that offers them: show
`quickSwitchChoices` and hand one to `quickSwitch(choice)`, which goes through
`apply`, so it gets the countdown and only *Keep* saves it. *Mirror* copies the
focused monitor. A mirror's own mode and position say what it's copying, so what
it was before goes in its entry's `arrangement` for *Extend* to bring back;
`setups.lua` ignores that field. *<monitor> only* leaves everything where it was
for the same reason. A monitor mirroring another stays one of Quickshell's
screens, so `isMirroring(port)` is what hides its bar.

## Keep-awake

`KeepAwake.qml` is the shell's one keep-awake. Its `on` and selected `duration`
are never saved, so it starts off with "until turned off" on every shell
start. The control center tile and the switch in the keep-awake popup both
toggle it; the keep-awake bar element, always shown, opens that popup and
shows a filled cup while it is on. Turning it on uses the duration chosen
in the popup (until turned off, 30 min, 1 h or 2 h); choosing one while on
restarts the countdown, and the popup shows `secondsLeft`. When a countdown
runs out it turns off and sends a "Keep-awake ended" notification through
`notify-send`; turning it off by hand sends none. Those decisions live in
`KeepAwakeState.js`. While on it holds an `IdleInhibitor` on a transparent,
click-through 1×1 window of its own, because an inhibitor only counts while
its window is shown and the control center hides its window when closed. The
`keep-awake toggle` IPC call (`modules/KeepAwake.qml`, bound to ALT+SHIFT+I)
toggles it too and is the only toggle that shows the OSD, labelled by
`KeepAwakeState.osdLabel`.

## Night light

`NightLight.qml` is the shell's one night light, driven from the control
center. While `on` it runs `hyprsunset -t <temperature>` (through `sh`, so a
missing hyprsunset exits 127), and stopping it gives the screen its colours
back. The slider saves `nightLightTemperature` in `appearance.json` and a
running hyprsunset follows it live through `hyprctl hyprsunset temperature`.
`on` is never saved. When hyprsunset exits while night light is on, night
light turns off and `failureHint` says why; an exit it asked for is no
failure, and turning it back on while the old hyprsunset is still exiting
starts a new one once it exits. The bounds, the commands and the
on/off decisions are plain functions in `NightLightState.js`, tested without
Quickshell.

## Screen shares

`ScreenShares.qml` is the shell's one reader of the screens other apps share
through PipeWire. It reads the graph once and keeps when each share was first
seen (`shares`), and every bar's recording indicator shows them. Which nodes
are a shared screen (not a camera or a virtual camera) and the start times
are decided in `components/bar/RecordingIndicator.js`, tested without
Quickshell.

## Screen capture integration

`ScreenCapture.qml` detects `grim`, `slurp`, `wf-recorder`, and `wayshot` at runtime.
It saves captures to `$(xdg-user-dir PICTURES)/Screenshots`; the service only runs
fixed executable argument lists and passes the selected region directly from `slurp`.

`shell.qml` creates it once, for tool detection and IPC actions, and hands
it to the bar, the control center and the chooser (`modules/ScreenCapture.qml`,
which owns the `screen-capture toggle` IPC call).

Replace the existing `SUPER + SHIFT + S` binding with:

```lua
hl.bind(win .. " + SHIFT + S",
    hl.dsp.exec_cmd("quickshell ipc --path ~/.config/quickshell call screen-capture toggle"))
```

The chooser supports `1`/`Enter` for a region screenshot, `2` for the focused
display, `3`/`4` for recordings when `wf-recorder` is installed, and `R` or
`Escape` to stop a recording.

## App menu bridge

`AppMenuBridge.qml` is the shell's one bridge to the menus apps export over
D-Bus, which the app menu bar element shows after the app's name. It runs
`app-menu-bridge.py` (python3 with python-gobject) while something shows the
app menu (`setUsing`): an enabled app menu bar element, or the app menu
popover, which can open at any time and so keeps it running. It tells the
script the focused window (pid, title, whether it runs under XWayland) and
keeps what it answers as `exported`, for `exportedPid`.
For an XWayland window the script finds the menu two ways:
DBusMenu menus registered with `com.canonical.AppMenu.Registrar` (Electron,
Java, Qt on X11), and the `org.gtk.Menus` menubar GTK apps export through
`appmenu-gtk-module`, found from the `_GTK_*` properties of their X11 windows
(read with `xprop`). Hyprland doesn't tell X11 window ids, so a menu is the
focused window's when the D-Bus connection exporting it has the window's pid
(`GetConnectionUnixProcessID`); among several, the one whose X11 window has the
same title wins. A native Wayland window has neither, so the script looks
through the objects its process exports for a window's menubar published by
`appmenu-gtk-module` (`/org/appmenu/gtk/window/menus/menubar/<n>`) or a
`GtkApplication`'s (`<app>/menus/menubar`). Empty ones don't count, which is how
a hidden menubar is exported, and a process with several windows that could own
the menu shows none: nothing tells them apart, and an item could act on the
wrong one. It follows the menu's change signals and hands it over again
when it changes, and runs the items chosen (`activate`). What it hands over is
raw; `components/AppMenuModel.js` (`exportedMenus`) makes menus of it, tested
without D-Bus. With no registrar, no `xprop`, no python-gobject or an app that
exports nothing, the app menu shows the shell's menus only; the reason goes to
the Quickshell log once.
