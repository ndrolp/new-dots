# Services

Place shared system integrations here, such as audio, network, and battery services.

## Cava

`Cava.qml` is the one `cava` process the shell shares. Each Cava bar element
calls `setDrawing(element, drawing)` as it starts or stops being drawn; cava
runs while any is drawn and stops otherwise. It listens to the default audio
output and restarts when the default changes. It computes the most bars any
drawn element asks for (its `barCount`, a bar profile option), restarting when
that changes, and each element resamples the frame down to its own count. Its
config is generated by `CavaOutput.js` and given to cava on stdin.

`silent` turns true once cava has printed only flat frames for
`CavaOutput.silenceDelay` (or isn't running), and the Cava bar element hides
meanwhile. A hidden Cava still counts as drawn, so cava keeps listening for the
sound that shows it again.

When cava exits on its own while drawn, it is tried again a while later and
`failureHint` says why the bars stay flat (missing, failed to start, or
stopped unexpectedly after printing frames). When to start, stop, restart and
retry is decided by plain functions in `CavaOutput.js` (`drawnChanged`,
`restartAsked`, `framePrinted`, `exited`, `retryDue`); `Cava.qml` only
carries the decisions out, so they are tested without Quickshell.

## Workspaces

`WorkspaceService.qml` is what the shell knows of Hyprland's workspaces and
windows, and how it acts on them. Which workspaces are listed (1 to 21), which
windows a workspace shows and the `hyprctl` commands that focus, move and create
are plain functions in `WorkspaceState.js`, tested without Quickshell. A move or
a new workspace that doesn't exist yet takes a second step, sending the workspace
to the monitor it was meant for, because Hyprland makes it on the focused monitor
or the one a rule names.

## Monitor setups

`MonitorSetups.qml` is the shell's one way to change the monitors. Displays and
the quick switch work out the entries they want with the plain functions in
`MonitorEntries.js` (`moved`, `withResolution`, `turnedOff`…) and hand them to
`apply(entries)`, which starts the 15-second countdown; `keep()` and `revert()`
answer it, and an unanswered one reverts. `entries`, `modesOf(port)` and
`savedSetups` are what there is to show, and `modules/MonitorChange.qml` shows
the countdown card and *Identify* on the screens. Hyprland owns the setups
(`docs/adr/0002-hyprland-owns-monitor-setups.md`): the shell writes
`~/.config/hypr/monitor-setups.json` atomically, then runs `hyprctl eval` on
`apply_now` in `hypr/modules/monitors/apply.lua`, which reads it without the
full config reload `hyprctl reload` would do.

`forget(combination)` removes a saved setup from the file and doesn't ask
Hyprland, so the monitors stay as they are until the next time it detects them.
Hyprland doesn't watch that file: only the config and the modules it requires.
It's refused during a countdown, when Revert would put the file back, and
`savedSetups` leaves out a change being tried out, which isn't saved yet.

A change has to be in the file for Hyprland to apply it, so it's in there before
it's kept, with what to go back to under `unkept` in the same write. Revert
applies the previous arrangement through the file, then puts the file back
exactly as it was, or removes it if there was none. `apply` refuses a setup
that leaves every screen dark, and any change when the saved file couldn't be
loaded: that's not the same as no file, and a write on top of it would lose every
saved setup. The steps are `MonitorChange.js`, snapping is
`MonitorArrangement.js` and mode and scale choices are `MonitorModes.js`, whose
`nearestScale` is the search Hyprland does, so a preset it won't take snaps
before it's written. All are tested without Quickshell. With a closed lid and an
external monitor the laptop screen is no part of a setup, by the same rule as
`split_by_lid` in `hypr/modules/monitors/setups.lua`: the two must stay in step.

Hyprland doesn't need the shell to get out of a change. If `apply_now` finds
`unkept`, Hyprland starts its own timer, a few seconds longer than the countdown,
and anything else that finds `unkept`, like a config load, goes back to what it
says and restores the file. A shell that starts first finds the same `unkept`
and reverts; either order ends the same. A countdown that finds `unkept` gone
ends there. `hyprctl` gets 5 seconds to answer, and *Revert* doesn't wait for it.
If Hyprland doesn't take something, the restored file is applied again, as a rule
that failed can leave some monitors changed.

`QuickSwitch.js` holds the quick switch's choices and the entries each one builds,
for the panel on SUPER+P and anything else that offers them: show
`quickSwitchChoices` and hand one to `quickSwitch(choice)`, which goes through
`apply`, so it gets the countdown and only *Keep* saves it. *Mirror* copies the
focused monitor. A mirror's own mode and position say what it's copying, so what
it was before goes in its entry's `arrangement` for *Extend* to bring back;
`setups.lua` ignores that field. *<monitor> only* leaves everything where it was
for the same reason. A monitor mirroring another stays one of Quickshell's
screens, so `isMirroring(port)` is what hides its bar. A choice that changes nothing,
like *Extend* on monitors already extended, is saved straight away with no countdown.

`MonitorToast.js` decides the toasts. After each reading of the monitors, an
unknown combination sets `offeringChoices`, once for each time it appears; only
choosing or changing something saves it. Failures set `notice`, which
`modules/MonitorToast.qml` shows beside that toast on the focused monitor. Some of
them come from what Hyprland leaves beside the saved file: `.bad` for a file it
couldn't read, with a number after it if that name is taken, which
`monitor-notices.sh` moves to a `.bad.told` name of its own as it reads it so that
it's told once and no backup replaces another, and `.fallback`, the monitors whose
saved mode is gone, one per line, there for as long as that lasts. What's been told
survives a reload of the shell; a shell that restarts, rather than reloads, tells a
fallback again. Nothing is read or told while `locked`, so what happened meanwhile
comes up after unlock.

## Keep-awake

`KeepAwake.qml` is the shell's one keep-awake. Its `on` and selected `duration`
are never saved, so it starts off with "until turned off" on every shell
start. The control center tile and the switch in the keep-awake popup both
toggle it; the keep-awake bar element, always shown, opens that popup and
shows a filled cup while it is on. Turning it on uses the duration chosen
in the popup (until turned off, 30 min, 1 h or 2 h); choosing one while on
restarts the countdown, and the popup shows `secondsLeft`. When a countdown
runs out it turns off and sends a "Keep-awake ended" notification through
`notify-send`; turning it off by hand sends none. Those decisions live in
`KeepAwakeState.js`. While on it holds an `IdleInhibitor` on a transparent,
click-through 1×1 window of its own, because an inhibitor only counts while
its window is shown and the control center hides its window when closed. The
`keep-awake toggle` IPC call (`modules/KeepAwake.qml`, bound to ALT+SHIFT+I)
toggles it too and is the only toggle that shows the OSD, labelled by
`KeepAwakeState.osdLabel`.

## Power changes

`PowerChange.js` decides which power change event a reading of UPower's
display device makes (`reading`, `next`): plugging the charger in
(charging, waiting to charge or full) shows "Charging", unplugging
(discharging or empty) "On battery", and reaching 15% while discharging,
unplugging included, "Battery low" once, until the battery has been above
15% or plugged in, like `modules/LowBattery.qml`'s notification. An unknown
or waiting-to-discharge state says nothing about the charger. The first
reading, and one after a battery appears, is how it already was and shows
nothing; without a battery nothing shows. `modules/PowerChanges.qml` feeds
it and shows each event as `OsdChange.power`.

## Night light

`NightLight.qml` is the shell's one night light, driven from the control
center. While `on` it runs `hyprsunset -t <temperature>` (through `sh`, so a
missing hyprsunset exits 127), and stopping it gives the screen its colours
back. The slider saves `nightLightTemperature` in `appearance.json` and a
running hyprsunset follows it live through `hyprctl hyprsunset temperature`.
`on` is never saved. When hyprsunset exits while night light is on, night
light turns off and `failureHint` says why; an exit it asked for is no
failure, and turning it back on while the old hyprsunset is still exiting
starts a new one once it exits. The bounds, the commands and the
on/off decisions are plain functions in `NightLightState.js`, tested without
Quickshell.

## Screen shares

`ScreenShares.qml` is the shell's one reader of the screens other apps share
through PipeWire. It reads the graph once and keeps when each share was first
seen (`shares`), and every bar's recording indicator shows them. Which nodes
are a shared screen (not a camera or a virtual camera) and the start times
are decided in `components/bar/RecordingIndicator.js`, tested without
Quickshell.

## Web apps

`WebApps.qml` is the shell's one view of the web apps on this machine, for
the web app maker. `webapps.py` does the file and network work, one command
at a time, answering in JSON: `list` reads the `.desktop` files in
`~/.local/share/applications` marked `X-Webapp=true` (the URL is in
`X-Webapp-Url`), `probe` fetches a page with curl for its name (the
manifest's `short_name`, else `application-name` or `og:site_name`, else the
`<title>`) and its largest icon (manifest, link icons, `/favicon.ico`, then
Google's favicon service), `icon` converts a local image picked with zenity,
`create` writes the entry (`google-chrome-stable --app=<url>`, the window
class Chrome gives it as `StartupWMClass`) with its icon as a 256 px PNG in
`~/.local/share/icons/hicolor/256x256/apps`, and `delete` removes both. Icons
are converted with ImageMagick and wait in `~/.cache/ndro-shell/webapps`
until created. A probe answer for a URL no longer in the field is dropped.
Which text is a URL, the fallback name, duplicates (the exact URL only) and
the window class are plain functions in `WebApps.js`, tested without
Quickshell; `tests/webapps.sh` tests the script on a scratch folder.

## Printers

`Printers.qml` is the Printers panel's view of the printers CUPS has added.
It reads them only while `watching` (the panel is open), every 3 seconds,
with `lpstat -l -p -d -v` under `LC_ALL=C`, and nothing runs while the panel
is closed. *Set default* runs `lpadmin -d` and *Remove* `lpadmin -x`; the
user is in `wheel`, which CUPS on Arch takes as an admin group, so neither
asks for a password. Parsing lpstat (state, the reason CUPS gives, network
or USB from the device URI, ipp-usb's localhost IPP counting as USB, the
default) and the commands are plain functions in `Printers.js`, tested
without Quickshell. The open printer's print jobs (`jobsPrinter`) are read
with the list, over IPP with `ipptool`, and *Cancel* runs `cancel`. After
a change the list is read again only while the panel is open.

`DiscoveredPrinters.qml` finds the printers not added yet, only while
`watching`: `avahi-browse -rpk` streams `_ipp._tcp` and `_ipps._tcp`
printers as they appear and go, and is stopped when the panel closes. USB
printers come through ipp-usb, which advertises them on `lo`. `shell.qml`
creates it next to the printers service, hands it the added printers and
reads them again after an add; the panel module (`modules/Printers.qml`)
sets `watching`. *Add* runs `lpadmin -p <model> -E
-v <uri> -m everywhere` (driverless, no password for `wheel`) with a
`dnssd://` URI for a network printer and ipp-usb's `ipp://localhost:<port>`
for a USB one. If avahi-daemon isn't running it says so and tries again
every 5 seconds. Parsing avahi-browse (its `\DDD` escapes, the TXT record,
one printer seen several ways), whether a printer is already added (its
uuid, dnssd name, host, or ipp-usb port in an added printer's device URI,
from `lpstat -v`) and the command are in `PrinterDiscovery.js`, tested
without Quickshell.

## Android devices

`AndroidDevices.qml` is the Android devices panel's view of the Android
devices and known devices. It uses whatever `adb` is on PATH, checked on
every open; without one the panel says to install `android-tools`. Only
while `watching` (the panel is open) it reads `adb devices -l` and `adb mdns
services` every 2 seconds; nothing runs while the panel is closed. An
ip:port connection that neither a known device's address nor its name
places is asked once for `ro.serialno`. Every device connected over the
network is remembered in `config/android-devices.json`, which belongs to the
machine and is gitignored, once its serial is known (an ip:port stands in
until then); nothing connects on its own. *Connect* runs `adb connect` on
the address mDNS announces, then the last one remembered; what adb answers
is matched loosely, and a failure that names neither the network nor
pairing is reported as either. *Disconnect* runs `adb disconnect`;
*Connect wirelessly* reads, over USB, the source address of the Android
device's default route (`ip route get 1.1.1.1`, unless it goes over mobile
data, else any `wlan*` address), runs `adb tcpip 5555` and connects to it.
Each action's label and the method that runs it come from one table,
`rowActions`. Parsing adb, merging the rows, the address Connect tries,
what `adb connect` answered and the commands are plain functions in
`AndroidDevices.js`, tested without Quickshell.

`AndroidPairing.qml` pairs new Android devices, only while `watching`.
`shell.qml` creates it next to the Android devices service, whose mDNS
services and rows it reads and whose `connectPaired` connects an Android
device it paired. It draws a fresh QR code
(`WIFI:T:ADB;S:<name>;P:<password>;;`, with `qrencode` into
`$XDG_RUNTIME_DIR`; the name starts with `studio-`, as Android Studio's
do) on every open, runs `adb pair` once the Android device announces the
code's `_adb-tls-pairing` service (or, if adb is busy then, once it is
free), and connects it when it announces itself. If that connect fails, or
nothing connects within 20 s, it says why instead of "Paired,
connecting…". The QR payload, the pairing services and what `adb pair`
answered are in `AndroidPairing.js`, tested without Quickshell;
`tests/android-pairing.sh` runs `AndroidPairing.qml` in a headless `qs`
with a fake adb.

## Scanners

`Scanners.qml` is the Printers panel's view of the scanners SANE can see.
Like the printers service it lists them only while `watching`, every 5
seconds, with `scanimage -f` (fields split by tabs), leaving out webcams
(the `v4l` backend); sane-airscan, escl and `net` devices are network,
the rest USB. It checks once per opening that sane-airscan is loaded
(`/etc/sane.d/dll.d/airscan` or `dll.conf`) and says why network scanners
can't show up when it isn't. When a scanner's scan view opens it reads the
colour modes the scanner offers (`scanimage -d <scanner> -A`, its `--mode`
option) and offers only those: Lineart, Binary, Halftone or "Black & White"
are black and white, and a remembered mode the scanner lacks falls back to
the nearest one it has. A scan runs `services/scan.sh`, which makes the
folder and runs `scanimage --format=pdf|png -p -o` into
`~/Pictures/Scans/scan-YYYY-MM-DD-HHMMSS.<ext>`. scanimage 1.4 writes
`<file>.part` and renames it when done, so the file being there is what
tells a saved scan; a failed one's `.part` is removed, and the file is
never deleted (scanimage's error is shown even when it was saved). It reads
progress from stderr, and on success sends a notification whose *Open* runs
`xdg-open` and *Show in folder* hands the file manager the encoded
`file://` URI over `org.freedesktop.FileManager1` (opening the folder
otherwise). The last settings are `scanSettings` in `appearance.json`,
starting at 300 dpi, colour and PDF. Parsing, naming, the colour modes, the
commands, progress, errors and the settings are plain functions in
`Scanners.js`, tested without Quickshell; `tests/scan.sh` tests `scan.sh`
with a fake scanimage.

## Screen capture integration

`ScreenCapture.qml` detects `grim`, `slurp`, `wf-recorder`, and `wayshot` at runtime.
It saves captures to `$(xdg-user-dir PICTURES)/Screenshots`; the service only runs
fixed executable argument lists and passes the selected region directly from `slurp`.

`shell.qml` creates it once, for tool detection and IPC actions, and hands
it to the bar, the control center and the chooser (`modules/ScreenCapture.qml`,
which owns the `screen-capture toggle` IPC call).

Replace the existing `SUPER + SHIFT + S` binding with:

```lua
hl.bind(win .. " + SHIFT + S",
    hl.dsp.exec_cmd("quickshell ipc --path ~/.config/quickshell call screen-capture toggle"))
```

The chooser supports `1`/`Enter` for a region screenshot, `2` for the focused
display, `3`/`4` for recordings when `wf-recorder` is installed, and `R` or
`Escape` to stop a recording.

## App menu bridge

`AppMenuBridge.qml` is the shell's one bridge to the menus apps export over
D-Bus, which the app menu bar element shows after the app's name. It runs
`app-menu-bridge.py` (python3 with python-gobject) while something shows the
app menu (`setUsing`): an enabled app menu bar element, or the app menu
popover, which can open at any time and so keeps it running. It tells the
script the focused window (pid, title, whether it runs under XWayland) and
keeps what it answers as `exported`, for `exportedPid`.
For an XWayland window the script finds the menu two ways:
DBusMenu menus registered with `com.canonical.AppMenu.Registrar` (Electron,
Java, Qt on X11), and the `org.gtk.Menus` menubar GTK apps export through
`appmenu-gtk-module`, found from the `_GTK_*` properties of their X11 windows
(read with `xprop`). Hyprland doesn't tell X11 window ids, so a menu is the
focused window's when the D-Bus connection exporting it has the window's pid
(`GetConnectionUnixProcessID`); among several, the one whose X11 window has the
same title wins. A native Wayland window has neither, so the script looks
through the objects its process exports for a window's menubar published by
`appmenu-gtk-module` (`/org/appmenu/gtk/window/menus/menubar/<n>`) or a
`GtkApplication`'s (`<app>/menus/menubar`). Empty ones don't count, which is how
a hidden menubar is exported, and a process with several windows that could own
the menu shows none: nothing tells them apart, and an item could act on the
wrong one. It follows the menu's change signals and hands it over again
when it changes, and runs the items chosen (`activate`). What it hands over is
raw; `components/AppMenuModel.js` (`exportedMenus`) makes menus of it, tested
without D-Bus. With no registrar, no `xprop`, no python-gobject or an app that
exports nothing, the app menu shows the shell's menus only; the reason goes to
the Quickshell log once.
